1. Big picture how the domains connect

The core lifecycle: a maintenance need becomes a job, a department raises a block request for it, the optimizer turns approved work into a block on a track, and that block's impact on trains is recorded. Everything else in the schema supports one of these five entities.

5. Blocks / optimizer output the plan

An optimization_run produces one or more schedule_versions; each version holds the actual blocks (possessions). Junction tables tie a block to the jobs it schedules, the requests it satisfies, and the trains it disrupts.

        string horizon
        string solver_status
    }
    SCHEDULE_VERSIONS {
        int version_id PK
        int run_id FK
        int parent_version FK
        bool is_active
    }
    BLOCKS {
        int block_id PK
        int version_id FK
        int section_id FK
        int track_id FK
        string status
        timestamptz planned_start
        timestamptz planned_end

    BLOCK_JOBS {
        int id PK

6. Real-time & monitoring live state + audit

Append-only, timestamped tables. realtime_events is the incident log; the three *_live_status tables answer "what is the state right now" for trains, tracks, and assets. Reroutes and audit actions reference this layer.
